What the embedding model does

Beacon uses sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2. A real local inference produced a 384-dimensional float32 vector: 384 numbers for each text, approximately 1,536 bytes for the raw vector, excluding document text and database overhead.

The question and handbook passages are converted into vectors. Similar directions help find passages with related meaning even when the words differ. Beacon also uses keyword and spelling search. Selected evidence is sent to DeepSeek, which writes the response. The embedding model retrieves information; it does not generate the answer or click CRM buttons.

Why this model: multilingual search is useful for English and Hindi/Hinglish questions, and its compact CPU runtime avoids a separate hosted embedding charge. That is the design reason, not proof it is the best model for every query. The current tokenizer limits an input to 128 tokens, so long passages can lose information. Retrieval quality still needs evaluation.

How to explain it: “The embedding model converts a question and our documentation into 384-number representations. We use their similarity to find relevant documentation. DeepSeek then answers using that evidence, and Playwright opens the selected CRM screen.”

The complete request flow

Visitor types or speaks → Soniox transcribes microphone audio → Beacon FastAPI backend validates the session → LangGraph loads conversation context → local search finds handbook evidence and CRM screen candidates → DeepSeek selects a response and demo → Pydantic validates the decision → Playwright opens the permitted screen while the answer is prepared → an evidence check reviews the answer → text and Microsoft speech reach the visitor.

Customer registration is a separate form workflow. Name, email and phone are saved through the reviewed CRM form. A durable submission receipt prevents the same registration from being saved again after an uncertain response. Model-generated text is not used as authorization to create arbitrary records.

Reliability changes and their limits

The application now records a demo checkpoint and attempts one automatic sign-in recovery when authentication expires. It restores the page, captured record identity and supported unsaved walkthrough state before retrying a read-only action. A record that is no longer visible is not replaced with a different lead. Save operations are never automatically replayed after an uncertain result.

Reuse of HTTPS connections removes repeated connection setup. A selected screen opens while answer generation continues. These are implemented optimizations; a model choice alone does not guarantee instant responses. Password failures, MFA, permission changes and network outages can still require operator action.

The current application still supports one active demonstration at a time. Larger traffic budgets are deployment planning scenarios, not proof of supported concurrency. Browser capacity, CPU/RAM, queueing and load tests must be planned before public rollout.

How the estimate is calculated

Current configuration: Soniox STT only, Microsoft edge-tts for replies. Soniox TTS is disabled and contributes $0 below. No paid Azure Speech API is configured; this is not an Azure production pricing quote.

  1. Demo sessions = monthly visitors × Beacon engagement × sessions per engaged visitor.
  2. Question turns = demo sessions × average questions per session.
  3. DeepSeek input includes instructions, history and evidence across planning, answer and checking calls. Default allowance: 12,000 input and 1,000 output tokens per turn, plus 4,000 input and 300 output for qualification per session. These are budget allowances, not measured averages.
  4. Soniox STT counts the entire streamed audio duration, including silence, plus transcript text. Default per voice turn: 30 streamed seconds and 10 seconds of actual speech. No custom context text is sent by the integration.
  5. Soniox TTS counts input text and generated audio. Default: 350 answer characters and 20 seconds of audio per voice turn, plus an 8-second, 120-character greeting per voice session.
  6. Live-preview traffic = turns × 50 preview seconds × 3 frames/second × 60 KB/frame. Website traffic adds 3 MB per visitor. All image and traffic values require measurement.
  7. Total = fixed hosting/database/monitoring allowance + (model + STT + TTS + bandwidth) × 1.20 reserve. Peak and off-peak totals vary only the DeepSeek rates; cache savings are not assumed.

At default token allowances, a text question costs $0.0024–$0.0048 in DeepSeek charges, before per-session qualification, speech and infrastructure. Counting only this number is not an all-inclusive demo cost.
